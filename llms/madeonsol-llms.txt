# MadeOnSol

> A Solana and Robinhood Chain data/intelligence platform for trading bots, AI agents, trading desks and data products — structured KOL, wallet, deployer, token, DEX and trading-signal data via REST, WebSockets and webhooks, with MCP tool access and x402 pay-per-call access for autonomous agents — plus an independent ecosystem directory of 1,200+ Solana & Robinhood Chain tools, dApps, and projects, with independent reviews, live uptime monitoring, and fee comparisons.

## About

MadeOnSol (madeonsol.com) is a Solana and Robinhood Chain (chain id 4663) data/intelligence platform for trading bots, AI agents, trading desks and data products. It provides structured KOL wallet tracking, deployer intelligence, and all-DEX trade streams — through Deployer Hunter, KOL Tracker, and the wider REST/WebSocket/webhook API — with MCP tool access and x402 pay-per-call access for autonomous agents, live on both chains. MadeOnSol also operates an independent ecosystem directory covering Solana and Robinhood Chain: 1,250+ tools across 32 categories, each listing carrying community reviews, uptime health scores, pricing details, and verified claim status.

### Deployer Hunter (Live Intelligence)
- Tracks 1,200,550+ Pump.fun token deployers — every pump.fun create indexed, 85K+ profiled with a reputation tier, alerts fire for the elite/good subset with historically high bonding rates
- Real-time alerts when tracked deployers launch new tokens
- Deployer tier system: Elite = 5+ deploys, 5+ bonds, ≥40% lifetime bond rate AND ≥50% recent; Good = 3+ deploys, 3+ bonds, ≥25% lifetime AND ≥30% recent; Moderate = 3+ deploys, 1+ bond, ≥15% / ≥15%; Rising = 100% on 1-2 resolved deploys; Cold = 3+ deploys with 0% on the last 10 outcomes. Only Elite/Good are "tracked" (alerted)
- Average Pump.fun bonding rate is 1-3%; tracked deployers average 25-40%+. A pump.fun token graduates (bonds) when its curve fills — roughly 85 SOL of buys — and migrates to PumpSwap (pump.fun's own AMM), not to Raydium

### KOL Tracker (Live Intelligence)
- Monitors 2,050+ curated Solana KOL (Key Opinion Leader) wallets in real-time
- Live trade feed showing every buy/sell within seconds of on-chain confirmation
- **Full historical trade data** retained per KOL — unlimited retention since 2026-06-05 (previously 180 days); PnL leaderboard windows remain today/7d/30d/90d/180d
- PnL leaderboard with five time windows: today, 7-day, 30-day, 90-day, and 180-day
- On-site Watchlist: registered users can track up to 30 KOLs and get a personalized feed
- Community ratings and wallet comparison tools
- **Scout Signal** — first-KOL-touch events on tokens, ranked by per-KOL "scout score" (mv_kol_scout_score, refreshed hourly). 38d backtest: top scouts (S-tier) attract ≥3 follow-on KOLs within 4h ~50% of the time vs ~14% baseline. Public leaderboard at /kol/scouts. API: `GET /api/v1/kol/first-touches` (REST), `kol:first_touches` WebSocket channel (PRO+), webhook subscriptions (Ultra: 10, Business: 50).

### Sniper Alerts — Pre-Confirm Pump.fun Deploys (Pro + Ultra)
- Pre-confirmation pump.fun deploy detection. New token launches surface in the feed a median ~290ms before they confirm on-chain (measured head start in production against CONFIRMED-stream deployer alerts: 24 h to 2026-09-20, n = 37,957 reconciled deploys, p10 160ms / p90 401ms; the confirmed stream is first on ~3.4% of launches).
- Tier policy: PRO is curated to elite/good-tier deployers; ULTRA receives every tier plus the `all` scope, custom watchlists, and the by-deployer feed.
- Multi-region detection for high availability.
- Delivery: webhook (`sniper:deploy` event) or WebSocket channel (`sniper:deploys`).
- Filterable by deployer tier (elite / good / moderate / rising / cold) or custom watchlist (Ultra).
- Read API for backtesting: `GET /v1/sniper/recent` (Pro + Ultra), `GET /v1/sniper/by-deployer/{wallet}` (Ultra). Custom watchlist: `GET|POST /v1/sniper/watchlist` + `DELETE /v1/sniper/watchlist/{wallet}` (Ultra, max 50 deployers; body {wallet | wallets[], label?}).
- Each deploy on `/v1/sniper/recent` carries a `footprint` block — the slot-window snipe rollup (slots deploy−1..+3): buys, buyers, sol, supply_pct, sniper_wallet_buys, data_available, as_of (null for deploys younger than the 10-min settle window).
- Operator playbook on https://madeonsol.com/developer covers pre-built tx, priority fees + Jito tips, low-latency infra, deployer reputation filtering, buy params, exit triggers.

- Rule engines on Robinhood Chain (all four shipped 2026-08-02) — user-defined rules that push signals to you, rather than feeds you poll. Each rule carries its own webhook URL + HMAC-SHA256 secret and/or a WebSocket channel; these per-rule webhooks are separate from the generic `/api/v1/webhooks` registry (whose only RHC event is `rhc:kol_trade`). Quotas are per chain — Solana rules never consume RHC capacity.
  - POST|GET /api/v1/rhc/copytrade/subscriptions, GET|PATCH|DELETE /api/v1/rhc/copytrade/subscriptions/{id}, GET /api/v1/rhc/copytrade/signals — RHC copy-trade rules: mirror a set of tracked 0x wallets, sizing mode fixed | proportional | percent_source (amounts in ETH), filter on min_trade_eth. Delivery webhook | websocket | both; WS channel `rhc:copytrade:signals`. Limits PRO 3 rules × 5 wallets, ULTRA 20 × 50, BUSINESS 100 × 250. No MC band — the RHC trade producer emits no market cap, and a filter that silently never matched would be worse than its absence (PRO)
  - POST|GET /api/v1/rhc/price-alerts, GET|PATCH|DELETE /api/v1/rhc/price-alerts/{id}, GET /api/v1/rhc/price-alerts/events — RHC market-cap dip/recovery alerts. Same one-shot lifecycle as Solana (watching → dipped → recovered, dip_low ratchets down while dipped), baselined on rhc_token_prices at creation; token_address, drop_pct and recovery_pct are immutable. WS channel `rhc:price_alert:events`; events `rhc:price_alert:dip` / `rhc:price_alert:recovery`. **Latency differs from Solana: a few seconds, not the 250 ms Solana evaluation loop.** Alerts are evaluated as trades land on the chain trade feed (`rhc:dex_trade`), with price-table polls (every 5 s while the feed is degraded or a trade carried no market cap, 60 s otherwise) and a trade-tape replay after a feed outage as safety nets; the floor is the chain trade flush (about 2 s). The create response says so in an `evaluation` block (`mode: "event_driven"`). Do not size a strategy on the Solana 250 ms loop (PRO)
  - POST|GET /api/v1/rhc/kol/coordination/alerts, GET|PATCH|DELETE /api/v1/rhc/kol/coordination/alerts/{id} — RHC KOL coordination rules: fire when `min_kols` distinct tracked KOLs buy the same RHC token inside `window_minutes` at score ≥ `min_score`, with `cooldown_min` suppression and a `score_jump_break` early exit (a re-fire is flagged `is_rearm`). Optional MC band (an unknown cap is dropped, never assumed inside the band). WS channel `rhc:kol:coordination`. Scored by the same shared v1 scorer as Solana so the numbers compare, with two differences recorded per signal in `score_inputs`: `quality` is real (RHC KOL 7d winrate) while `earliness` is defaulted to 50, because RHC has no early-entry equivalent (PRO)
  - POST|GET /api/v1/rhc/kol/first-touches/subscriptions, GET|PATCH|DELETE /api/v1/rhc/kol/first-touches/subscriptions/{id} — push on the FIRST tracked-KOL buy of an RHC token. Backed by a dedicated first-touch table with UNIQUE (token_address) written by an insert trigger, so a second KOL buying the same token is silent — that is the definition of a first touch. Filters: kol, min_first_buy_eth, min_kol_winrate, strategy, min_mc_usd/max_mc_usd (strict schema — an unknown filter key is a 400, never silently ignored). No min_scout_tier / min_n_touches: RHC has no scout-score equivalent, so min_kol_winrate is the quality gate. WS channel `rhc:kol:first_touches`; event `rhc:kol:first_touch`. The subscription is ULTRA+; the raw WS channel is PRO+ and unfiltered

RESUME: keep a cursor `{instance, seq, ts}` of the last frame your handler finished processing (it returned, or its promise settled) and reconnect with `{"type":"subscribe","channels":[...],"resume":{"instance":...,"seq":...,"ts":...}}`. The `subscribed` ack echoes `resume` with `accepted:true` (`accepted:false`, `reason:"replay_in_progress"` plus a `warning` frame with that code if a replay is already running on the connection). Same instance and cursor inside the in-memory buffer (last 20,000 frames, about 6-8 minutes): frames re-sent from memory (`mode:"ring"`, with seq). Otherwise (server restart = `instance_changed`, or longer absence = `ring_truncated`): each channel rebuilt from storage from the cursor's `ts` (minus 60 s slack, deduped by id), bounded to 60 minutes, 2,000 rows per channel, 20,000 rows total (rhc:dex_trades and rhc:dex_trades_unattributed: 10 minutes back and up to 10,000 rows, which can include trades that were never pushed live). Rebuilt frames carry `seq:null`, `mode:"durable"`, `replayed:true`, and `partial:true` + `missing:[fields]` where a field is not stored. Partially rebuilt: kol:trades, kol:coordination (no kols[]), deployer:alerts, rhc:dex_trades(_unattributed), rhc:copytrade:signals, rhc:kol:coordination, rhc:token_locks. No stored source: token:graduations and rhc:new_tokens (memory buffer only, then gap `not_reconstructable`). token:prices gets the current price row per watched mint once (`snapshot:true`, `partial:true`). Every resume or legacy replay is bracketed by `replay_start` and `replay_end`, even with nothing to replay; `replay_end` has `sent`, `matched`, `complete`, `reason`, `retryable`, `retry_after_ms?`, `resume_ts_hint?`, `incomplete_channels?`, `last_seq`, `last_ts` (maxima over frames sent), `live_from_seq`, `count` (legacy, = matched) and `channels:{<ch>:{mode, sent, matched, complete, reason?, gap?, time_basis?, max_rows?, retryable?, retry_after_ms?, late_ingest_possible?, partial?, missing?, since_ts?, truncated_at_ts?, gap_before_ts?}}`; reasons: backpressure, instance_changed, ring_truncated, window_exceeded, row_cap, source_busy, source_error, late_ingest_possible, not_reconstructable. COMMIT RULE: replayed frames do not move your saved cursor, because a storage replay is sent channel by channel, not in one time order. On replay_end complete:true, commit {instance, seq: last_seq, ts: last_ts} (keep your previous value where one is null) and let live frames advance it again. On complete:false with retryable:true, keep the cursor you resumed from and resume again after retry_after_ms (from ts: resume_ts_hint ONLY when the reply carries one, which the server emits when every incomplete RETRYABLE channel was cut by row_cap (a channel with a FINAL gap, such as not_reconstructable on token:graduations or rhc:new_tokens, does not block the hint, because retrying could not fetch anything behind it); with a mixed retryable set, for example one row_cap and one source_error channel, there is no hint and you resume from your pre-resume cursor, because the hint would step past the failed channel's unread range. Per-channel truncated_at_ts is always there for a client that tracks channels separately); what arrives twice is dropped by id. On complete:false with retryable:false the reported gaps are final (not_reconstructable, window_exceeded, ring_truncated, instance_changed): backfill them from REST, then commit as for complete. SDK behaviour: on a retryable incomplete recovery our SDKs resume again on the same socket after retry_after_ms (up to maxResumeRetries, default 5), using resume_ts_hint only when every incomplete retryable channel is row_cap. The budget is per connection and its counter resets on every (re)connect. When that budget is spent, the gap event says exhausted:true: the client stops asking on that connection, the committed cursor stays where it is, and the next reconnect resumes again. On a FINAL gap they emit a gap event first (channels, reason, permanent, the server's bounds and the RANGE that may be incomplete as skipped.from -> skipped.to) with advancedPastGap:true and source:"auto", then move the cursor past it. A count of missing events is never given because it cannot be known. That advance is the client library's own decision, not your approval: set onUnrecoverableGap:"stop" to keep the cursor instead, which stops the stream and emits fatal with the same gap, and acceptGap() then re-reports it with source:"manual" and continues. WATERMARK AND HOLDBACK: a row's id or timestamp is assigned when it is written, not when it commits, so a row with a lower id can still appear after a read passed it. The server therefore advances the committable watermark only across rows whose writing transaction had already finished when the read took its snapshot (xmin_blocked:true when it stops early), holds it 5 s behind now (holdback_ms) and re-scans the last 60 s (rescan_ms) on the next resume; a stuck long transaction cannot freeze it forever (capped at maxHoldbackMs, reported as holdback_capped_ms). While the cap is in force the channel reports holdback_ms = 300000 (the nominal 5000 stays as nominal_holdback_ms) and its guarantee states the real bound and says CAPPED: about 6 minutes (5 min + the 60 s re-scan), not the usual 65 s.. Frames are still delivered as they are read; the holdback only limits what you may commit, and last_ts is held to the tightest safe_ts (per channel in replay_end.channels.<ch>.watermark {scheme, safe_ts, holdback_ms, nominal_holdback_ms?, holdback_capped_ms?, rescan_ms, xmin_blocked, gate_ms?, guarantee}, overall in replay_end.watermark_safe_ts). RECOVERY IS BOUNDED, NOT A COMPLETENESS GUARANTEE: with the id and ingest-time schemes a write whose transaction commits more than about 65 s after its id or timestamp was taken can be missed (about 6 minutes instead while holdback_capped_ms is set), and for rhc:dex_trades / rhc:dex_trades_unattributed (scheme producer_gate) recovery is bounded by the producer's 600 s freshness rule, so a trade already older than 600 s when it was ingested is not recoverable through this path at all. Each channel states its own bound in watermark.guarantee. LATE WRITES: every storage read pages by an ingest-time column, a storage id or the producer's own freshness window, so a row written late is not skipped; a channel that could not rule that out would report complete:false, reason late_ingest_possible, never complete:true. LOAD: recovery is limited server-wide; a resume waits up to 20 s for a slot, otherwise its storage-backed channels report reason source_busy with retry_after_ms (memory frames are still sent). A second replay request on a socket whose replay is still running gets only a replay_in_progress warning, no second replay_start / replay_end, so do not wait for one. Live frames arriving during a replay are held (up to 5,000 frames or 4 MB; price ticks coalesced per mint) and delivered after `replay_end`, skipping ids already sent. A socket that cannot drain during a replay gets `complete:false`, `reason:"backpressure"` and close 4008: reconnect and resume. Frames are lost only across a disconnect or a 4008 close, and the resume reply states what was and was not recovered. LEGACY: `replay_since_seq` / `replay_since_ts` still work, from memory only; `replay_start` now reports `replay_truncated:true` with `reason` instance_changed or ring_truncated instead of replaying nothing silently. If the server's own event-bus connection drops, missed events are re-read from storage and delivered with `replayed:true, recovered:"bus"`. ENTITLEMENTS: every frame is checked against the current plan; after a downgrade, channels above it are dropped with a `warning` `code:"channels_revoked"` (also a token:prices mint set above the new cap); revoking or rotating the API key deletes the stream token and open sockets close 4001 within about a minute. Subscribe filters are connection-wide: one filter object applies to every subscribed channel (e.g. action:"buy" also drops deployer alerts); use a second connection for channels that need different filters. SDK support (resume, dedupe, gap events, close-code handling) since npm madeonsol-x402 2.2.0, madeonsol 2.28.0, robinhood-chain-x402 0.13.0, robinhood-chain-sdk 0.9.0 and PyPI madeonsol-x402 1.31.0 / robinhood-chain 0.12.0 (older versions keep working without auto-resume; current published versions on https://madeonsol.com/mcp).

- Honesty notes: cost_basis_observable_from in response surfaces the data window cutoff (2026-04-12). Overflow sells (no matching buy in window) are silently discarded rather than fabricated. Mints without current price return unrealized_sol: null rather than fabricated zero. 50k-trade hard cap per wallet surfaces in notes.truncated_trades.

Params: wallet, action (buy/sell; transfers carry action null, filter them with event_type=transfer), event_type (swap/transfer), limit (max 200), before (block_time cursor). Full wallets, counterparties, and tx_signatures on all tiers.

### Token Intelligence
- GET /api/v1/token/{mint} — real-time VWAP price, market cap, 24h volume, **velocity deltas** (`mc_change_pct`, `volume_usd`, `mev_volume_pct` keyed by 5m/15m/1h/2h/4h windows), deployer reputation, KOL smart-money activity, `first_seen_at` + `age_seconds`, and `is_blacklisted` + `blacklist_category` (stablecoin/wrapped_sol/lst/rug) — all in one call. Also returns `liquidity_to_mc_ratio` (liquidity_usd / market_cap — structural thinness gauge), `launch_cohort_sol` (total SOL spent by the first 20 buyers), and `launch_cohort_size` (count of first-20 buyers present, 0–20). Invalid mints return structured 400: `code: "invalid_mint"`, `reason` (specific diagnosis — too short / too long / contains 0OIl), `received_length`, `expected_length`, `example`, `docs`.
- POST /api/v1/token/batch — same per-mint shape (including velocity deltas and the three cohort/liquidity fields above) for up to 50 mints in a single request (body: `{"mints":[...]}`). DB queries batched with IN(...); dex-stream + RPC fan out in parallel. ~10-20× cheaper than N sequential single-mint calls.
- GET /api/v1/tokens/search?q= — token SEARCH by symbol / name / mint prefix (all tiers, shipped 2026-08-16): q 1-64 chars, limit 1-50 (default 10); returns mint, symbol, name, price, market cap, liquidity, primary DEX. GET /api/v1/tools/search?q=&category=&limit= — search the Solana & Robinhood Chain tools directory (all tiers, limit ≤50).
- GET /api/v1/tokens/{mint}/candles — **PRO+** OHLCV candles from the trade firehose: tf 1m|5m|15m|1h|4h|1d (default 1h), from/to ISO, limit 1-1500 (one full day of 1m fits in one call); PRO the last 30 days, ULTRA/BUSINESS full retained history.
- GET /api/v1/tokens/{mint}/top-traders — **PRO+** every wallet that traded a mint ranked by realized SOL PnL or ROI (sort), window_days, min_bought_sol (default 0.1), limit/offset; PRO top 25, ULTRA/BUSINESS 100; enriched with is_kol / is_alpha_tracked / bot_confidence.
- POST /api/v1/tokens/batch/risk — **PRO+** the /tokens/{mint}/risk score for up to 50 mints in one call, body {"mints":[...]}.
- POST /api/v1/wallet/batch/trades — **PRO+** (2026-08-16) recent trades for up to 50 wallets in ONE call: body { wallets: string[] (1-50), since?: unix seconds (≤90 d back), limit_per_wallet?: 1-100 (default 20), action?: buy|sell }; one grouped result per wallet.
- Deployer Hunter REST (all tiers unless noted): GET /api/v1/deployer-hunter/alerts (limit 1-50 default 20, tier, priority high|medium|low, alert_type, token_mint, min_kol_buys, since/before + offset — cursor AND offset pagination on every tier), GET /api/v1/deployer-hunter/alert-stats?period=7d|30d|all (alert volume + outcome stats), GET /api/v1/deployer-hunter/leaderboard (sort bonding_rate|recent_bond_rate|total_bonded|last_deploy_at|post_bond_survival_rate, tier, limit/offset), GET /api/v1/deployer-hunter/best-tokens (period 7d|30d|all, limit 1-20), GET /api/v1/deployer-hunter/recent-bonds (limit 1-50, since, tier, peak_mc_min — pump.fun graduations → PumpSwap), GET /api/v1/deployer-hunter/stats, GET /api/v1/deployer-hunter/{wallet} (profile), GET /api/v1/deployer-hunter/{wallet}/tokens (limit 1-50 default 20, offset).
- Webhooks CRUD: POST|GET /api/v1/webhooks, GET|PATCH|DELETE /api/v1/webhooks/{id}, POST /api/v1/webhooks/test (PRO+).
- GET /api/v1/tokens/{mint}/pools — **PRO+** per-venue liquidity map: every DEX pool a token trades in (pump.fun/PumpSwap/Raydium/Meteora/Orca), live vs parked (is_active), fragmentation + top-pool share. Complements /token/{mint}'s single aggregate liquidity number. Returns pools[] (pool_address, dex, quote_mint, liquidity_usd, last_price_sol, last_swap_at, amm_id, is_active) + summary (pool_count, active_pool_count, dex_count, dexes, total_liquidity_usd, primary_pool, primary_dex, top_pool_share_pct).
- GET /api/v1/tokens/{mint}/risk — **PRO/ULTRA** transparent 0–100 token rug-risk / safety score. Returns `risk_score`, `band` (safe/caution/danger), an auditable `factors[]` array (each with status + points + detail: mint/freeze authority, liquidity depth & thinness, Token-2022 transfer fee, LP burn/lock (reads unknown: LP-token custody is not observed for Solana pools), bundled/sniped open, deployer track record, KOL distribution, supply_inflation, blacklist), raw `inputs`, and `score_version`. Every factor is inspectable (unlike an opaque score). Composed from the same data layer as `GET /token/{mint}` — no extra latency. **inputs.sniper_footprint (2026-07-10)**: slot-window snipe rollup (slots deploy−1..+3) — buys, buyers, sol, supply_pct, sniper_wallet_buys, data_available, as_of. Informational, does not move the score; data_available: false = outside capture window, not zero snipes. **dev block (2026-07-11)**: deployer self-activity — create-tx self-buy (buy_sol/buy_tokens/buy_supply_pct), post-create own-mint trading (bought_tokens_after, sold_tokens, sold_sol, first/last_sell_at), and live on-chain holdings (holdings_tokens, holdings_supply_pct, wallet_empty, transferred_out — chain balance well below trade-derived expectation ⇒ tokens moved out via transfer; null when not honestly assertable). dev: null for mints pre-dating the deploy pipeline.
- GET /api/v1/tokens/{mint}/depth — **PRO/ULTRA (2026-07-11)** per-pool **price-impact / slippage**: "how much SOL to move price 1/5/10%" (`to_move_price`) + impact and tokens received per buy size (`quotes[]`, `?sizes=` up to 8 SOL amounts, default 0.5,1,5,10). Exact for constant-product AMMs (PumpSwap, Raydium v4/CPMM, Meteora DAMM — from streamed reserves, source: "stream"); pump.fun/bonk bonding curves priced from a live read of virtual reserves (source: "live_rpc"). Honesty: per-pool (not router-optimal); concentrated pools (CLMM/Orca/DLMM) + unclassified return under `unsupported_pools[]` with a reason instead of a wrong number. A sharper liquidity-quality read than raw liquidity_usd.
- GET /api/v1/tokens/{mint}/trades — **PRO+** (2026-07-10) mint-scoped trade tape: every captured trade for one token, newest first, cursor-paginated. Params: limit (1-500, default 100), cursor, action (buy/sell), wallet, since/until (default full history). Per trade: tx_signature, wallet_address, action, sol_amount, token_amount, price_sol, price_usd, early_buyer_rank, slot, block_time, traded_at. Response carries coverage { history_start: 2026-04-12, scope: pump.fun pipeline }. The backfill complement to the live firehose.
- GET /api/v1/tokens — **PRO+** filtered token directory + trending/momentum board. Filters: min_mc, max_mc, min_liq (default 2000 — set 0 to disable dust floor), active_h, primary_dex (pumpfun/pumpswap/raydium/meteora/orca/raydium_clmm), authority_revoked, exclude_token2022, lp_burned. **Momentum filters are now fully DB-native** (read-time token_prices_trending view — sort + paginate correctly, no over-fetch): min_volume_1h_usd, max_mev_share_pct, min_liq_mc_ratio, max_liq_mc_ratio, mc_change_1h_min_pct, mc_change_1h_max_pct. Only deployer_tier (elite | good | moderate | rising | cold | unranked) remains a post-filter (over-fetches 3×). Sort: mc_desc / mc_asc / last_trade_desc / liquidity_desc / cumulative_volume_desc / **mc_change_5m_desc / mc_change_1h_desc / volume_1h_desc / trending** — `trending` = recent-volume × positive-momentum composite, recency-bounded to the last 1h, echoes filters.trending_version="v1". Returns tokens[] with mev_share_pct + organic_volume_1h_usd + mc_change_5m_pct + mc_change_1h_pct + is_token_2022 + liquidity_to_mc_ratio + deployer_tier.
- GET /api/v1/tokens/almost-bonded — **PRO+** pre-bond pump.fun tokens approaching graduation, ranked by **velocity** (Δbonding-progress/min) and enriched with **deployer reputation** — "95% and accelerating" beats "92% stalled". Nobody else ships pre-bond + reputation + velocity. Filters: min_progress (default 80), max_progress (default 99.99, excludes bonded), min_velocity_pct_per_min, max_age_minutes, deployer_tier, authority_revoked, min_liq. Sort: velocity_desc (default) / progress_desc / eta_asc. Returns tokens[] with mint, symbol, name, progress_pct, velocity_pct_per_min (null until a 5m snapshot exists), eta_minutes, stalled, real_sol_reserves, market_cap_usd, liquidity_usd, authorities_revoked, deployer_tier, age_minutes.
- `mev_volume_pct` is unique to MadeOnSol — surfaces the % of each window's volume tagged as sandwich/Jito-bundle MEV, so traders can flag wash-pump patterns where the headline volume is bot-driven rather than organic demand. Sourced from CONFIRMED-commitment swap stream (reorg-safe).
- Price computed from our own DEX trade stream (VWAP across 14 programs spanning 8 venues), market cap from price × on-chain supply
- All data self-hosted — no external API dependencies
